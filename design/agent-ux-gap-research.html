TL;DR

Hermes Bots has world-class agent plumbing and below-par agent surfaces. The transport layer (streaming, tool runs, approvals, interrupt/steer, reconnect replay, multi-bot groups) matches or beats ChatGPT/Claude. But everything the user actually reads and touches — code blocks, links, diffs, plans, artifacts, previews, browsing, voice — is behind the leaders, and several gaps are surprisingly cheap to close: the wire protocol already delivers inline_diff and todo.updated that the app silently drops, and the server already exposes file.attach, image.generate, /api/audio/transcribe, /api/audio/speak that the app never calls.

Strength Agent control loop

Approvals with once/session/always + sudo/secret variants, notification quick-actions, interrupt & steer, replay catch-up. Claude Code-grade consent UX already shipped.

Biggest gap Nothing to look at

No artifact/canvas/preview surface of any kind. A phone is a single column — leaders give the agent a second surface. This is where ChatGPT Canvas & Claude Artifacts win.

Quick wins Wire-ready, UI-absent

inline_diff diffs, todo.updated plan checklists, code copy buttons + language chips, clickable links. Days, not weeks — no protocol changes.

Differentiator Phone as the body

Termux-hosted gateway + termux-api bridge = the agent gets SMS, calls, torch, sensors, TTS, clipboard — consent-gated by the approval system we already have. Nobody in the leader pack does this.

01 State of the art — what the leaders ship (Sept 2026)

The 2026 consensus pattern: chat is no longer the product — chat is the control channel for a workspace the agent writes into. Every leader has moved output out of the scrollback and into a structured surface.

ChatGPT Canvas OpenAI

Inline editing surface · docs + code
  • Side-by-side editable document; agent makes pinpoint inline edits instead of regenerating — diff-highlighted so you see exactly what changed
  • Selection-scoped requests: highlight a sentence or function, ask for a rewrite of just that
  • Shortcut menus (adjust length, debug code, add comments, port languages)
  • Code: inline suggest-edit-apply loop with syntax highlighting and run/preview for web langs

Claude Artifacts Anthropic

Self-contained mini-app previews
  • Any substantial output (code, HTML, SVG, MD, React) opens in a dedicated pane — never floods the chat scrollback
  • Instant live preview of runnable HTML/React in a sandboxed frame
  • Version switching — every artifact edit keeps history; hop back to v1 with a dropdown
  • Shareable/publishable artifact links; remix culture around them

Cursor · Claude Code · Codex Agentic IDEs

Trust-but-verify work surfaces
  • Inline diffs as first-class review UI — approve/reject per hunk before an edit lands
  • Plan / todo checklists rendered live while the agent works (Claude Code's todo list is its trust anchor)
  • Terminal as a first-class surface — command output, PTY views, slash commands
  • Explicit plan-review stage before autonomous execution

Operator · Computer Use · Browser-Use Browser agents

"Watch it work" viewing
  • Live viewport of the agent's browser — you watch it click and type (OpenAI Operator's signature UX)
  • Session recordings & replay (Cloudflare Browser Run) — audit what the agent did
  • Snapshot/DOM views as lower-bandwidth alternative to video

Gemini Canvas + Stitch Google

Preview + generative design
  • Live code preview canvas; integration with Stitch (text/sketch → high-fidelity UI)
  • Deep Android integration path — on-device models (Gemini Nano / AICore) for system-level assistant behavior

Generative UI Emerging

AI renders the interface itself
  • Responses stop being text-with-markdown and become charts for trends, forms for actions, tables for comparisons — model emits structured UI, client renders native widgets
  • Research direction (A2UI, agentic canvases): the canvas is a surface agents read and write, dissolving the chat-vs-canvas boundary
  • Mobile-first versions of this are just starting to appear — open lane for a native app

02 Where hermes-bots stands today

From a full audit of the codebase (chat rendering, protocol catalog, manifest, data layer). The honest split: excellent control plane, minimal display plane.

Already strong Keep

Matches or beats the leaders
  • Streaming with caret, interim sealing, reader-gated autoscroll + jump-to-latest pill
  • Approvals: A/B/C choice cards, once/session/always/deny, sudo/secret/clarify variants, notification quick-actions
  • Steering — interrupt and mid-flight redirect, like ChatGPT's newest steering
  • Tool chips with humanized labels, duration, expandable args/output
  • Multi-agent groups + cross-gateway AnyChat rooms — genuinely unique vs. any leader
  • Fleet/Roster + Pulse approval inbox — an operations metaphor no consumer agent has
  • Robust reconnect w/ event replay (512×64 ring)

Display plane Behind

What the user reads
  • Markdown is hand-rolled: fences, inline code, bold, bullets, headings. Links aren't rendered at all (known deferral, MarkdownText.kt:25)
  • Code blocks: monospace box, horizontal scroll — no highlighting, no copy button, no language chip (the fence's language token is discarded in splitFences)
  • No tables, no math, no inline images (coil-compose is a declared dependency that is never used)
  • Copy = whole-bubble long-press only; no per-message actions, no regenerate/edit/share
  • inline_diff on tool.complete arrives over the wire and is ignored
  • todo.updated events arrive and are ignored — no plan/checklist surface
  • Transcripts not cached locally (server refetch only), no search

Absent surfaces Missing

Entire categories
  • Artifacts/canvas: none — and the protocol has no artifact concept at all. Closest primitives: unused rendered? message field, file.attach, /api/files/download
  • In-app browser: no WebView, no Custom Tabs, no URL cards. The agent browses server-side (browser_navigate, browser_click, browser_snapshot) and the user sees only a humanized label
  • Voice: no STT, no TTS (voice.record is catalog-only v2; server REST /api/audio/transcribe + /api/audio/speak exist unused)
  • Files: gallery image attach only — no documents, no camera capture
  • Image gen: image.generate catalog'd (v2), never called
  • Terminal: PTY views deferred since README v1; cli.exec/shell.exec sit in the catalog unused
Manifest reality check: the app requests exactly two permissions — INTERNET and POST_NOTIFICATIONS. Zero device surface (camera/mic/location/SMS/sensors) is exposed to the agent. That's a deliberate, defensible security posture — but it also means the "AI on your phone" story is currently all cloud. The Termux bridge (§4.5) is the way to add device powers without bloating the app's permission surface.

04 Deep dives & suggestions

The five areas you asked about, plus the Termux play. Each dive ends with a concrete recommendation that respects the Fleet/Pulse spec's constraints.

4.1 · Code blocks — the cheapest credibility win

MissingEffort S–M

Today a fenced block renders as a monospace box with horizontal scroll; the language token from the fence is thrown away by splitFences() and there is no copy affordance — long-press the whole bubble is the only way. Every leader ships the same triad: language chip, copy button, highlighting.

Recommendation

  • Parse the fence language (```kotlin → chip label) — trivial change in MarkdownText.kt
  • Copy icon on the block header row with haptic + snackbar, reusing the existing copyOnLongPress plumbing
  • Highlighting without a WebView: either adopt compose-richtext/Markwon (note: Markwon is View-based; prefer a Compose-native tokenizer) or extend the hand-rolled renderer with a lightweight regex tokenizer for the ~10 languages your bots actually emit (kotlin, python, ts, bash, json, sql, xml, yaml, go, rust). Keywords/strings/comments/numbers covers 90% of perceived quality
  • While in there: wrapped vs. scroll toggle (long lines), and line-count cap with "Show all" (the ToolChip already established this pattern)
  • Fix links in the same pass — they're the other documented deferral, and URL cards (favicon + title + domain, via the existing OkHttp stack) make bot research replies dramatically more scannable

4.2 · Artifacts / canvas — the big one

MissingEffort L + protocol

No artifact concept exists anywhere in the app or the protocol. The leaders' lesson is blunt: once outputs get big, the chat column is the wrong place for them. Claude moves them to a pane with versions; ChatGPT moves them to an editable canvas with pinpoint diffs. On a phone you can't do side-by-side — but you can do the mobile-native equivalent.

Recommendation — an artifact sheet, not a canvas

  • Surface: a bottom-sheet / full-screen artifact viewer opened from an inline "artifact card" in the transcript (title, type icon, version badge) — the mobile idiom Claude's app uses
  • Types, phased: (1) code (reuses §4.1 renderer) and markdown (styled doc view) → (2) SVG (Compose ImageVector/vector parser — no JS needed) → (3) images (image.generate output) → (4) HTML preview last, via the two-step in the note below
  • Versions: keep an artifact-version stack per session; header shows v3 with a back/forward affordance — Claude's most-loved artifact feature and nearly free once artifacts are event-sourced
  • Share/export: system share sheet + save-to-files via FileProvider — makes artifacts feel like real products, not chat exhaust
  • Seed it with what's already on the wire: the rendered? field on message.complete is unused — define it as "detached rendered payload" and you have artifacts v0 without touching the turn loop. Full design in §6
Spec tension, resolved: fleet-pulse-ui-spec.md forbids WebView/JS runtimes — keep that rule for the app shell. For artifact preview specifically: (a) code/md/SVG/images render natively, no WebView; (b) HTML gets a "Open preview" → Chrome Custom Tab (sandboxed by the browser, not embedded, spec-compliant); (c) if full in-app HTML preview ever becomes non-negotiable, propose a single, tightly-scoped renderer-only WebView isolated from app data as an explicit spec amendment — never quietly.

4.3 · In-app browser — you already have the data

MissingEffort M

The agent browses server-side — browser_navigate, browser_click, browser_snapshot — and the app reduces all of it to a humanized chip label ("Open page", "Click page"). Meanwhile Operator's single most praised feature is simply letting the user watch.

Recommendation — three tiers

  • Tier 1 (S): URL cards + Custom Tabs. Linkified sources in replies (needs §4.1 links); tapping opens Chrome Custom Tabs — in-app feel, zero WebView, zero spec violation
  • Tier 2 (M): snapshot strip. browser_snapshot results (already flowing) become a horizontally scrolling thumbnail strip on the tool chip: tap → fullscreen image viewer with the page title + URL + "Open" button. This is Operator's UX at 1% of the cost — no video stream, just the screenshots the agent takes anyway
  • Tier 3 (L, optional): live viewport. If the gateway ever streams screenshots (or a low-fps MJPEG over the existing WS), a "Watch" button on working-state cards. Defer until Tier 2 proves demand

4.5 · Phone-as-body — the Termux:API bridge (nobody else has this)

DifferentiatorEffort L

Termux:API exposes 70+ device functions as shell commands. A gateway instance running in Termux (Python/Node — whatever hermes gateways run on) can wrap these as agent tools, and suddenly the agent can act on the physical phone. Critically, hermes already owns the hard part: the consent layer — the approval system (once/session/always/deny, sudo variants) is exactly the permission gate phone actions need, and the bot-relay architecture means the phone can host a bot that other gateways' bots can message.

Recommended shape

  • Keep the app's permission surface clean: the app keeps INTERNET + POST_NOTIFICATIONS; all device access lives in the Termux-hosted gateway sandbox (user explicitly installed and owns it). Android permissions land on the Termux:API app, not hermes-bots
  • Tool namespaced as phone.* with per-tool default approval policy (SMS/call/photo = always-ask; sensors/battery = auto; clipboard-read = ask)
  • Surface in Pulse: phone actions appear as existing tool chips + approval cards — no new UI paradigms needed; maybe a "This Phone" machine card in Fleet when a Termux gateway is paired
  • Marketing line writes itself: "The AI agent that lives in your pocket and can actually use the phone." No leader ships this

4.6 · Diffs & plan checklists — free trust, already on the wire

Wire-readyEffort S

Two of the highest-trust UI elements in agentic coding — inline diffs (Cursor/Claude Code review flow) and live todo checklists (Claude Code's plan anchor) — are already defined in PROTOCOL.md and already arriving: inline_diff on tool.complete, and todo.updated interleaved during turns. The app parses the events and renders neither.

  • Diff view: red/green monospace rows inside the expandable ToolChip (or a sheet for long diffs), matching the fleet dark palette. ~1–2 days
  • Todo/plan card: a pinned collapsible checklist under the working-status while streaming — items flip to done as todo.updated events land. This single component does more for perceived competence than anything else on this page

06 Protocol draft — artifact support Proposal only

PROTOCOL.md is the authoritative wire contract — nothing below exists today. This is a starting point for a spec PR, designed to reuse the existing event-stream and approval idioms (names follow the established domain.verb style).

// --- artifacts: detached rendered outputs, versioned per session ---

// client asks server to promote/refresh an artifact (or agent does it unprompted)
{ "method": "artifact.update",
  "params": { "session_id": "…", "artifact_id": "site-v1",
              "kind": "html" | "markdown" | "code" | "svg" | "image" | "data",
              "title": "Landing page", "language": "html",
              "content": "…",           // full content (small artifacts)
              "version": 3, "parent_version": 2 } }

// streamed as events during a turn (same interleaving as tool.* events)
"artifact.opened"   { artifact_id, kind, title, version }
"artifact.delta"    { artifact_id, version, text }        // stream large bodies
"artifact.closed"   { artifact_id, version, final: true }

// history + fetch (mirrors session.events.since semantics)
"artifact.list"     → [{ artifact_id, kind, title, latest_version, updated_at }]
"artifact.get"      { artifact_id, version? } → { content, kind, title, … }

// client-side rendering hint on messages (formalizes the unused `rendered` field)
message.complete { …, "rendered": { "artifact_id": "site-v1", "version": 3 } }

// phone-as-body tools on a Termux-hosted gateway (P4; approval-policied)
tools: "phone.sms.send", "phone.sms.read", "phone.call", "phone.contacts",
       "phone.location", "phone.sensors", "phone.battery", "phone.torch",
       "phone.tts", "phone.clipboard", "phone.camera", "phone.notify"
Design notes: artifacts are session-scoped and version-pinned so reconnect replay (session.events.since) reconstructs artifact state for free, exactly like tool runs today. artifact.update with parent_version enables the Claude-style version chain. The phone.* namespace is gateway-local — it requires zero changes to the app-facing protocol beyond normal tool chips + approvals.
